# Pattern Quality Analysis

## Objective
Analyze the patterns generated by our ML pipeline (BERTopic + HDBSCAN) to determine if they represent legitimate, specific vehicle defect patterns.

## Quality Criteria
A GOOD pattern should:
1. Be specific to ONE make/model (e.g., "Toyota Camry" not "Toyota + Honda")
2. Have a reasonable year range (2-6 years, not 20+ years)
3. Focus on a specific component/issue type
4. Contain complaints that are semantically related

A BAD pattern would:
1. Mix multiple unrelated makes/models
2. Have absurdly wide year ranges
3. Group unrelated issues together
4. Contain complaints that don't actually relate to each other

### Section 5: Problematic Patterns Identified

#### Problem 1: Cross-Make Contamination (CRITICAL - 86% affected)
BERTopic clusters complaints by TEXT similarity, not vehicle similarity. So all "forward collision avoidance" complaints get grouped together regardless of whether they're about Ford, Toyota, or Honda vehicles.

The `getPatternMetadata()` function then picks ONE make/model (often wrong) to represent the entire cluster.

#### Problem 2: Duplicate Patterns (26 duplicate groups)
Multiple BERTopic clusters get assigned the SAME make/model/component metadata, creating duplicates like:
- 47 patterns all labeled "HONDA CR-V STEERING"
- 23 patterns all labeled "HONDA CR-V ELECTRICAL SYSTEM"

#### Problem 3: yearEnd=9999 Bug (3 patterns)
Some patterns have invalid year ranges due to missing year data in complaints.

#### Problem 4: Wrong Component Assignment
Even when make/model might be correct, components are often wrong:
- Brake complaints assigned to "FUEL SYSTEM"
- Engine complaints assigned to "ELECTRICAL SYSTEM"

### Section 6: Conclusions & Recommendations

#### Overall Assessment: **PATTERNS ARE NOT USABLE**

The current patterns are **fundamentally broken** and should not be shown to users. 86% have cross-make contamination, meaning they mix complaints from completely different vehicle manufacturers.

#### Root Cause Analysis

The problem is **architectural**, not a bug:

1. **BERTopic clusters by text similarity** - This is working correctly! It groups all "airbag deployment" complaints together because they have similar text.

2. **But we want clusters by VEHICLE + ISSUE** - A pattern should be "2018-2020 Tesla Model 3 airbag issues", not "airbag issues across all vehicles".

3. **Metadata extraction happens AFTER clustering** - By the time we try to extract make/model, the cluster already has mixed vehicles, so we pick the wrong one.

#### Recommended Solutions

**Option A: Pre-filter before clustering (RECOMMENDED)**
1. First, group complaints by make+model
2. Run BERTopic SEPARATELY on each vehicle's complaints
3. This ensures patterns are vehicle-specific by design

```
Example flow:
- Tesla Model 3 complaints → BERTopic → "Tesla Model 3 airbag pattern"
- Toyota Camry complaints → BERTopic → "Toyota Camry brake pattern"
```

**Option B: Post-filter after clustering**
1. After BERTopic clustering, split mixed clusters by make/model
2. Create sub-patterns for each vehicle within a cluster
3. More complex but preserves cross-vehicle similarity info

**Option C: Add vehicle metadata to embeddings**
1. Prepend make/model to complaint text before embedding
2. "TESLA MODEL 3: Airbag deployed while driving..."
3. BERTopic will naturally separate vehicles in embedding space

#### Immediate Actions

1. **Do NOT show current patterns to users** - They are misleading
2. **Implement Option A or C** - Pre-filter is simplest
3. **Add validation** - Reject patterns where >10% of complaints have different make
4. **Fix yearEnd=9999 bug** - Use current year if no valid year found
